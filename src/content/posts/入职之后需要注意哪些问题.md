## 一、建立良好的人际关系

和同事处好关系，融入团队，是很多人会忽视的。认为程序猿只要搞好技术就行了，其实是大错特错。 你要清楚，你是一个新人，刚进入这个行业，你必然会遇到一堆连不上环境、摸不清流程的坑。这时候，团队里如果能有一个愿意随口提点你两句的‘自己人’，能帮你省掉几个小时甚至一天的瞎折腾。因此，人际关系的基础一定要提前打好，切忌在遇到麻烦时才临时抱佛脚，那种带有强目的性的求助往往效果很差，也容易引起别人反感。 社会很现实：如果大家关系好，你的技术失误那叫‘新人正常踩坑’，大家笑笑就帮你解了；如果大家看你不顺眼，你写错一个标点符号那都叫‘能力不行’。更别忘了，‘团队融入度’本身就是领导决定你试用期去留的隐形考核指标。

当然，这里说的“建立关系”，不是让你去刻意讨好谁， 而是让你在进入新环境后，不要把自己完全封闭起来。

那应该怎么做？

其实不需要太刻意，也不需要一上来就搞复杂的人情往来。 更重要的是做到以下几点：

-   主动和同事打招呼，不要总是过于封闭
-   平时有机会时，正常参与聊天和吃饭，不要总是一个人闷着
-   遇到别人帮助你时，及时表达感谢
-   在工作配合上积极一点，让别人感受到你是愿意沟通、愿意配合的人

有时候一些小的善意动作，比如一起买水、顺手帮忙、请大家喝个饮料， 当然也可以起到拉近关系的作用。

## 二、尽快熟悉开发流程

入职后，要尽快搞清楚公司的开发流程和规范。

### 1、了解公司的开发环境

**需要了解的内容：**

-   公司有哪些开发环境（开发环境、测试环境、生产环境）
-   每个环境的用途和访问方式
-   环境之间的配置差异

### 2、明确 Git 协作流程

**需要搞清楚的问题：**

-   公司使用什么 Git 协调开发的工作流程是什么
-   分支命名规范是什么
-   提交代码的流程是怎样的
-   Code Review 的标准是什么

> **记住：这些问题要大胆地问，尽早搞清楚。**

不懂就问，总比因为不懂而犯错要好得多。

## 三、开发任务前的准备

在给你开发任务的时候，有几个关键点一定要注意。

### 1、需求必须搞清楚

**开发前要确认：**

-   需求的具体逻辑是什么
-   有哪些边界情况需要处理
-   输入输出是什么
-   有哪些异常场景需要考虑

> **不要没搞清楚需求就开始写代码，这样很容易返工。**

### 2、确定开发分支

**开发前要确认：**

-   应该在哪个分支上开发
-   分支是从哪里拉取的
-   开发完成后要合并到哪里

> **一定要搞清楚在哪个分支开发之后，再写代码。**

避免写完代码才发现分支搞错了，需要重新来过。

## 四、工作态度和表现

刚入职的前几个月，你的工作态度和表现非常重要。

### 1、态度要端正

**第一印象很重要：**

-   刚开始多加加班
-   尽量保证安排的任务都能按时完成
-   表现出积极的态度

> **第一印象一旦形成，后面就很难改变了。**

### 2、不要心虚，放平心态

**正确的心理状态：**

-   自信一些，不要一上来就觉得自己什么都不行
-   承认自己有不足，但也要承认自己有基础
-   既然能通过面试进入公司，就说明具备一定的能力

> **既不要妄自菲薄，也不要盲目自大。**

### 3、少说话，多做事（技术层面）

**技术上的"少说话"是指：**

-   没有把握的话不要说
-   对于不了解的领域，先去了解再发表意见
-   多听别人说，多学习

**为什么不说更好？**

-   你不说，别人可能会认为你对待技术很严谨
-   说了一些比较低级的问题，别人很容易看出你的水平

**多做事是指：**

-   本职工作要主动承担
-   领导给的其他事情也要积极配合
-   表现出你的积极性

### 4、多说话，多沟通（非技术层面）

**非技术上的"多说话"是指：**

-   尽快通过沟通融入到团队中去
-   建立起自己的朋友圈
-   参与团队的讨论和活动

> **总结：技术严谨少说话，融入团队多沟通。**

## 五、提前做好准备

如果时间比较充裕，可以做一些提前准备。

### 1、提前写测试接口

**为什么要提前写？**

-   熟悉项目框架的代码结构
-   提前排雷，了解常见的坑
-   保证后续给你任务时，能够快速上手

**怎么做？**

-   在项目框架里面写个测试接口
-   熟悉接口的调用方式
-   了解数据库的连接方式
-   熟悉常见的工具类和组件

## 六、Git 操作注意事项

Git 操作一定要谨慎，一个小错误可能导致严重后果。

### 1、不明确的操作先备份

**操作前要做的事：**

-   不确定的操作，先备份当前代码
-   确保出问题时可以快速恢复

### 2、Pull 前先 Commit

**为什么要这样做？**

-   方便回滚
-   避免代码冲突时丢失自己的修改

**操作流程：**

```
1. 先 commit 自己的修改
2. 再 pull 远程代码
3. 如果有冲突，解决冲突
4. 最后再提交
```

### 3、切换分支前先 Commit

**为什么要这样做？**

-   避免切换分支时把未提交的修改带到其他分支
-   保持代码的清晰和可追溯

> **记住：本地有修改时，一定要先 commit 再切换分支。**

## 七、风险报备意识

当任务可能无法按时完成时，一定要提前报备。

### 1、为什么要提前报备？

**提前报备的好处：**

-   给领导留出调整计划的时间
-   给团队留出应对措施的时间
-   避免到最后才发现问题，影响整个项目进度

### 2、什么时候报备？

**报备的时机：**

-   发现需求比自己预想的复杂
-   遇到无法解决的技术问题
-   发现需要依赖其他人的工作
-   意识到时间可能不够

> **在规定时间内搞不出的需求，一定要提前找 leader 把风险报备上去。**

不是等到最后一刻才说，而是发现问题就要及时沟通。

## 八、保持正确的学习节奏

刚入职时，很容易受到老员工的影响，要注意保持自己的节奏。

### 1、不要好高骛远

**要认清的现实：**

-   目前这份工作是你还能学到东西的
-   你是初次入职，还有很多需要学习
-   项目虽然可能有问题，但也是学习的机会

### 2、围绕公司项目去学习

**正确的学习方式：**

-   围绕公司项目去学习
-   把工作中遇到的问题当成学习机会
-   不要跟着老员工吐槽项目

### 3、不要受老员工影响

**老员工的吐槽不代表你的感受：**

-   老员工可能已经工作了几年
-   他们的节奏和你的不一样
-   你的节奏不要受老员工的影响

> **记住：这是你的第一份工作，围绕公司项目去学习，保持自己的节奏。**

* * *

## 九、关于包装经验的注意事项

这是一个比较敏感但非常重要的问题。

### 1、不要跟任何同事说

**无论关系多好：**

-   不要跟任何同事说你的经验是包装的
-   即使别人怀疑你，也不要承认

### 2、可以承认自己菜

**正确的应对方式：**

-   可以承认自己菜
-   可以承认自己经验不足
-   可以承认自己有些东西不会

### 3、菜很正常，包装不正常

**为什么可以承认菜？**

-   菜的程序员是很多的
-   菜可以通过学习变强
-   菜不代表你能力有问题

**为什么不能承认包装？**

-   包装涉及诚信问题
-   一旦承认，别人对你的信任会大打折扣
-   可能会影响你的职业发展

> **总结：可以承认自己菜，但不要承认自己包装经验。**
